# 需要人工决策的事项清单

> 工具能自动改的是**语法形状**；改不了的是**业务语义**。
> 下表把「`--fix` 做不到什么」写清楚 —— 这比宣称"全自动迁移"有用得多。

分两类：
- **A 类 · 完全不能自动改**：改写形状取决于主键结构、业务约束或事务边界，工具猜不出来
- **B 类 · 能自动改，但有残留决策**：机械替换可以完成，但替换完还需要人拍一个板

---

## A 类：完全不能自动改

| 规则 | 卡在哪 | 需要你决定的事 | 可选项 | 建议默认 |
|---|---|---|---|---|
| **R003** `DELETE/UPDATE ... LIMIT` | 改写形状取决于主键结构与删除规模 | ① 用什么键定位这一批 ② 单批多大 ③ 换成"一次删完"还是循环删 | ① `ctid` 子查询 ② 主键区间 `id BETWEEN` ③ 应用层循环 ④ 分批任务化 | **主键区间**；无主键的表才用 `ctid`（`ctid` 会随 vacuum 变化，不能跨事务持有） |
| **R005** `INSERT IGNORE` | 两者语义不等价，改写即行为变更 | 原来被**静默吞掉的数据错误**（截断、NOT NULL、类型不匹配）要不要暴露成失败？ | ① 暴露（改 `ON CONFLICT DO NOTHING`）② 保持静默（先在应用层过滤）③ 改 `ON CONFLICT (key) DO NOTHING` 指定目标 | **暴露**。静默吞错误是技术债，迁移是一次还债的机会 —— 但要提前告知业务方 |
| **R006** `ON DUPLICATE KEY UPDATE` | PG 的冲突目标**必须显式指定**，MySQL 可以从任意唯一索引推断 | ① 冲突目标选哪个唯一索引 ② 表上有**多个**唯一索引时怎么办 ③ `VALUES(col)` 改成 `EXCLUDED.col` 是否等价 | ① 指定单列/复合唯一索引 ② 拆成多条语句 + 应用层分支 ③ 改用 `MERGE` | 选**业务主键**那个唯一索引。**多个唯一索引的表必须拆**：MySQL 的"任一唯一键冲突即更新"语义，PG 单条 `ON CONFLICT` 表达不了 —— 这是最容易漏的陷阱 |
| **R007** `AUTO_INCREMENT` | 涉及 DDL 与数据迁移两个阶段 | ① 用 identity 还是 sequence ② 序列起点怎么定 ③ 原有 id 是否保留 | ① `GENERATED BY DEFAULT AS IDENTITY` ② 显式 `SEQUENCE` + `nextval` ③ `BIGSERIAL`（等价于②的语法糖） | **identity + 迁移后 `setval` 到 max(id)**。忘了这一步，第一条插入就主键冲突 |
| **R019** `REPLACE INTO` | 语义是"先删后插"，改写必然改变行为 | ① 能否接受触发器只触发一次 ② 能否接受自增主键不再跳号 ③ 关联表的外键级联是否会失效 | ① 改 `ON CONFLICT DO UPDATE` ② 保留删插语义（手工写两条语句） | **改 upsert**。但必须先确认没有依赖"删后插"副作用的逻辑（软删除、审计触发器、外键 `ON DELETE`） |
| **R015** `ON UPDATE CURRENT_TIMESTAMP` | 不是 SQL 改写，是架构选择 | ① 用触发器还是应用层维护 ② 时区怎么定 | ① `BEFORE UPDATE` 触发器 ② MyBatis 拦截器/`MetaObjectHandler` ③ 每张表手工改 | **应用层**。触发器在后续迭代里最容易被人忘记，且调试成本高；时区统一用 **UTC 存储 + 展示层转换** |

## B 类：能自动改，但要人拍板一个点

| 规则 | 能自动改的部分 | 残留决策 | 可选项 | 建议默认 |
|---|---|---|---|---|
| **R001** `IFNULL` | 全部 | 无 | —— | 直接改 `COALESCE` |
| **R002** `DATE_FORMAT` | 常见格式符（`%Y%m%d%H%i%s`） | ① 少见格式符（`%W` `%M` `%r` `%T`）要人工映射 ② 输出语言依赖 locale | ① 用映射表覆盖常见项 ② 人工核对剩余 | 映射表覆盖 `%Y%m%d%H%i%s%f %W %M`，**其余打 warning 不硬改** |
| **R004** 分页语法 | 全部 | 无 | —— | 直接改 `LIMIT ... OFFSET ...` |
| **R008** `GROUP_CONCAT` | 函数名与参数顺序 | ① 原 `SEPARATOR` 值 ② 是否带 `DISTINCT` ③ **MySQL 有 `group_concat_max_len` 默认 1024 截断，PG 无此限制** —— 改写后结果可能变长，下游字段够不够宽 | ① 保持原分隔符 ② 加 `DISTINCT` 保留 ③ 下游字段扩宽或加 `substring` 截断 | 保持原语义。**主动检查下游字段长度**，这是静默截断变成静默溢出的经典坑 |
| **R009** 反引号 | 引号替换 | **大小写折叠**：MySQL 在 Windows 下标识符不区分大小写；PG 的 `"User"` 是区分大小写的。改成双引号后，所有查询必须统一大小写 | ① 全部转小写（改动面大，但一劳永逸）② 保留原大小写加双引号（查询必须严格一致） | **全部转小写**。迁移期就统一，比上线后慢慢踩好 |
| **R010** `LIMIT` 无 `ORDER BY` | 无法自动改 | ① 用哪一列排序 ② 无唯一键的表怎么办 | ① 主键/唯一键 ② 业务时间戳 + 主键作 tiebreaker ③ 保持原样（接受不确定） | **用唯一键排序**。没有唯一键的表先补一个 |
| **R011** `<foreach>` | 无法自动改 | ① 空集合怎么兜 ② 单批上限多少 | ① `<if>` 包住整段 ② 传哨兵值 `IN (NULL)` ③ 应用层判空 ④ 批量大小 ≤ 参数上限 | ① `<if>` 包住最直观 ② **PG 单语句绑定参数上限 65535**，批量插入按 `65535 / 每行参数数` 算单批行数 |
| **R012** `REGEXP` | 运算符替换 | ① **大小写敏感默认不同**：MySQL 8.0 前 `REGEXP` 不区分大小写，PG 的 `~` 区分 ② 正则方言（POSIX vs PCRE）③ 反向引用与转义 | ① `~`（区分）② `~*`（不区分）③ 改 `regexp_match` 并显式加 `(?i)` | **`~*`**（保持 MySQL 的不区分大小写行为）。**这一条特别容易静默出错，必须人工确认原来是否依赖不区分大小写** |
| **R013** `JSON_EXTRACT` | 路径改写 | ① 用 `->` 还是 `->>` ② 列类型要不要从 `json` 迁到 `jsonb` ③ jsonb 会重排 key、去重 key | ① `->>` 做文本比较 ② `->` 需要 jsonb 类型 ③ 迁 jsonb（可建索引） | **`->>` + 迁 jsonb**。`->` 带引号，拿它比字符串不会报错但永远不相等 |
| **R014** `TINYINT(1)` | 类型替换 | ① `BOOLEAN` 还是 `SMALLINT/INT` ② ORM 的 typeHandler 要不要改 | ① `BOOLEAN` ② `SMALLINT`（保持数字语义） | **`BOOLEAN`**。但要检查 MyBatis 映射与前端入参是否依赖 `0/1` |
| **R017** `DESC` + `LIMIT` | 可自动加 `NULLS LAST` | **保持 MySQL 行为还是改成 PG 默认** | ① `NULLS LAST`（等价 MySQL）② `NULLS FIRST`（等价 PG 默认）③ 建表时加 NOT NULL | **`NULLS LAST`**（保持行为不变是迁移第一原则）。能加 NOT NULL 的列加 NOT NULL，从根上消除 |
| **R018** 索引前缀 | 可自动生成 `CREATE INDEX` | ① 表达式索引 vs `pg_trgm` GIN vs 全文检索 ② 查询要不要同步改 | ① `left(col, n)` 表达式索引 ② `pg_trgm` + `GIN`（支持模糊匹配）③ 全文索引 | 看用途：**等值/前缀匹配用表达式索引**；`LIKE '%x%'` 用 `pg_trgm`。**查询必须用同一表达式，否则索引白建** |
| **R020** 日期函数 | 函数与区间语法替换 | ① 格式串映射 ② 时区（`now()` 是事务时间戳，`CURRENT_TIMESTAMP` 语义细节不同）③ `UNIX_TIMESTAMP` 的时区含义 | ① `col + INTERVAL '1 day'` ② `TO_DATE` ③ `EXTRACT(EPOCH FROM ...)` | 统一 **UTC** 存储。`UNIX_TIMESTAMP()` 在 MySQL 里受 `time_zone` 影响，PG 的 `EXTRACT(EPOCH)` 对 `timestamptz` 才等价，**对 `timestamp` 会少一次时区换算** |

## 跨规则的整体决策（工具完全不覆盖）

| # | 决策点 | 为什么必须人定 | 建议默认 |
|---|---|---|---|
| 1 | **事务隔离级别**：MySQL 默认 RR，PG 默认 RC | 同一条语句在两种隔离级别下结果可能不同，且只在并发下暴露 | 明确选定并在连接串/会话上固定，**不要依赖默认值** |
| 2 | **字符集与排序规则**：`utf8mb4_general_ci` → PG 的 ICU collation | 大小写、重音敏感性不同，直接影响 `ORDER BY` 与**唯一约束是否成立** | 显式指定 collation，不要用库默认 |
| 3 | **时区**：`TIMESTAMP` / `DATETIME` / `timestamptz` | MySQL 的 `TIMESTAMP` 带时区转换，PG 的 `timestamp` 不带 | 统一 **UTC 存储**，展示层转换 |
| 4 | **数据迁移本身** | 工具只看 DDL/SQL，不搬数据 | 迁移与结构变更分开，先迁数据再切流 |
| 5 | **存储过程 / 触发器 / 函数** | 方言差异远大于 SQL，需要重写 | 能挪到应用层的就先挪 |
| 6 | **自增与序列在**多实例**下的分配** | identity 有缓存步长，多节点可能跳号 | 提前告知业务方"id 会跳号" |
| 7 | **大偏移分页**（`OFFSET 100000`） | PG 的 OFFSET 是扫描后丢弃，深分页会退化成全表扫 | 改用游标分页（`WHERE id > ? LIMIT n`） |
| 8 | **`\|\|` 的语义** | MySQL 默认当逻辑或，PG 当字符串拼接 | 迁移期立即全局排查，改为 `CONCAT()` |

## 谁来决策

| 决策类型 | 应由谁拍板 |
|---|---|
| 主键/索引/分区/序列/隔离级别/collation | DBA 或数据库负责人 |
| 空值语义、排序、分页、字段长度、JSON 结构 | 业务开发负责人 |
| 交互行为变化（排序变化、重复数据合并、错误暴露） | 产品经理 + 业务方确认 |
| 触发器 vs 应用层、批量大小、迁移顺序 | 技术负责人 / 架构 |
