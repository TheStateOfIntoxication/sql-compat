## R001 · IFNULL 无对应函数

- **级别**：BLOCKER
- **检测**：SQL 文本中出现 `IFNULL(`（大小写不敏感）
- **改写**：`IFNULL(a, b)` → `COALESCE(a, b)`
- **为什么是 BLOCKER**：Kingbase/PostgreSQL 没有 `IFNULL`，语句直接报错，不会静默降级
- **误报风险**：低。`IFNULL` 是保留是 MySQL 专有函数名

## R002 · 日期格式化

- **级别**：BLOCKER
- **检测**：`DATE_FORMAT(` 出现
- **改写**：`DATE_FORMAT(col, '%Y-%m-%d %H:%i:%s')` → `TO_CHAR(col, 'YYYY-MM-DD HH24:MI:SS')`
- **注意**：函数名要换，**格式串也要换**（`%Y` → `YYYY`，`%i` → `MI`），这是最容易漏的
- **误报风险**：低

## R003 · DML 不支持 LIMIT

- **级别**：BLOCKER
- **检测**：`DELETE` / `UPDATE` 语句中出现 `LIMIT`
- **改写**：
  ```sql
  -- MySQL
  DELETE FROM t WHERE created_at < ? LIMIT 1000;
  -- Kingbase / PostgreSQL
  DELETE FROM t
   WHERE ctid IN (SELECT ctid FROM t WHERE created_at < ? LIMIT 1000);
  ```
- **为什么用 `ctid`**：PG 系没有 MySQL 的 `LIMIT` on DML，但可以用 `ctid`（行物理标识）做子查询定位
- **误报风险**：中。正则限制在 2000 字符窗口内匹配，超长语句可能漏检而非误报（漏检可接受，误报不可接受）
- **已知缺口**：`DELETE ... USING ...` 组合场景未覆盖
