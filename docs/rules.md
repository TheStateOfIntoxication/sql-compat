## 关于 v0.1 定稿时的语义调整

有 4 条规则在实现阶段改了定义。原因相同：**原本设想的问题在纯文本层面无法可靠检测**，
而一个永远不触发（或永远误报）的规则，比没有规则更糟 —— 它会让整份报告失去可信度。

| ID | 原设想 | 实际实现 | 为什么改 |
|---|---|---|---|
| R010 | `ctid` 行标识提示 | **`LIMIT` 无 `ORDER BY` → 行序未定义** | 原设想是 INFO 级知识提示，不是"问题"；换成"分页无排序"这个真实存在、不报错但结果会变的坑 |
| R016 | 隐式类型转换 | **`<=>` → `IS NOT DISTINCT FROM`** | 隐式转换需要列类型信息，无 schema 无法判断；`<=>` 是确定性的语法差异 |
| R017 | NULL 排序 | **`ORDER BY DESC` + `LIMIT` 时的 NULL 位置** | 单独看 `ORDER BY` 无法判断 NULL 是否真的影响结果；叠加 `LIMIT` 才构成“翻页翻错”的实际风险，误报也大幅下降 |
| R020 | 子查询 `LIMIT` | **`DATE_ADD` / `DATE_SUB` / `STR_TO_DATE` / `UNIX_TIMESTAMP`** | 现代 PG 对子查询 `LIMIT` 已无限制，原规则基本不成立；日期函数是迁移里最高频的残留 |

### R017 的 `LIMIT` 限制后来被自己的用例证伪了一半

上面 R017 那条的理由写的是“没被截断的结果里这个差异并不构成实际问题”。
这句话在 v0.3 的运行时对比里被自己推翻了一半：

| 用例 | 语句 | 静态层 | 运行时 |
|---|---|---|---|
| `07_distinct_owners` | `SELECT DISTINCT owner_id ... ORDER BY owner_id`（ASC，无 `LIMIT`） | 0 问题 | **DIFFERENT**，第一行 `NULL` vs `1` |
| `92_known_order_null_desc` | `ORDER BY owner_id DESC, id ASC`（DESC，无 `LIMIT`） | 0 问题 | **DIFFERENT**，第一行 `id=13` vs `id=14` |

即使不翻页，两库返回的**顺序不同**也是实实在在的差异：取 `list.get(0)`、做下拉框默认值、
按顺序写文件、拿两边结果集 diff，全都会中招。

但放宽到“所有可空列的 `ORDER BY`”又不现实——没有 schema 就不知道列可不可空，
对每条 `ORDER BY` 都报会让报告彻底变成噪音。所以当前维持 `LIMIT` 门槛，
把盲区写进 [`known-limitations.md`](known-limitations.md)，并靠第二层兼底。

## R001 · IFNULL 无对应函数

- **级别**：BLOCKER
- **检测**：SQL 文本中出现 `IFNULL(`（大小写不敏感）
- **改写**：`IFNULL(a, b)` → `COALESCE(a, b)`
- **为什么是 BLOCKER**：Kingbase/PostgreSQL 没有 `IFNULL`，语句直接报错，不会静默降级
- **误报风险**：低。`IFNULL` 是 MySQL 专有函数名

## R002 · 日期格式化

- **级别**：BLOCKER
- **检测**：`DATE_FORMAT(` 出现
- **改写**：`DATE_FORMAT(col, '%Y-%m-%d %H:%i:%s')` → `TO_CHAR(col, 'YYYY-MM-DD HH24:MI:SS')`
- **注意**：函数名要换，**格式串也要换**（`%Y` → `YYYY`，`%i` → `MI`），这是最容易漏的
- **误报风险**：低

## R003 · DML 不支持 LIMIT

- **级别**：BLOCKER
- **检测**：`DELETE` / `UPDATE` 语句中出现 `LIMIT`
- **改写**：
  ```sql
  -- MySQL
  DELETE FROM t WHERE created_at < ? LIMIT 1000;
  -- Kingbase / PostgreSQL
  DELETE FROM t
   WHERE ctid IN (SELECT ctid FROM t WHERE created_at < ? LIMIT 1000);
  ```
- **为什么用 `ctid`**：PG 系没有 MySQL 的 `LIMIT` on DML，但可以用 `ctid`（行物理标识）做子查询定位
- **误报风险**：中。正则限制在 2000 字符窗口内匹配，超长语句可能漏检而非误报（漏检可接受，误报不可接受）
- **已知缺口**：`DELETE ... USING ...` 组合场景未覆盖

## R004 · 分页语法

- **级别**：BLOCKER
- **检测**：`LIMIT <a>, <b>`（逗号形式），同时支持 MyBatis 占位符 `LIMIT #{offset}, #{pageSize}`
- **改写**：`LIMIT 10, 20` → `LIMIT 20 OFFSET 10` —— **参数位置互换**，这是最容易被机械替换写错的地方
- **误报风险**：低。`LIMIT 10 OFFSET 20` 无逗号，不会命中

## R005 · INSERT IGNORE

- **级别**：BLOCKER
- **改写**：`INSERT IGNORE INTO ...` → `INSERT INTO ... ON CONFLICT DO NOTHING`
- **语义差异（必须人工确认）**：MySQL 的 `INSERT IGNORE` 会把数据错误（截断、NOT NULL）降级为 warning 继续执行；
  `ON CONFLICT` **只处理冲突**。改写后原本被静默吞掉的错误会变成失败 —— 这通常是好事，但是行为变更

## R006 · ON DUPLICATE KEY UPDATE

- **级别**：BLOCKER
- **改写**：`ON DUPLICATE KEY UPDATE col = VALUES(col)` → `ON CONFLICT (key) DO UPDATE SET col = EXCLUDED.col`
- **两个必改点**：
  1. `ON CONFLICT` 的**冲突目标列是强制的**，MySQL 可以从唯一索引推断，PG 系不能
  2. `VALUES(col)` 在 PG 里无意义，必须换成 `EXCLUDED.col`
- **实现**：规则会从语句里抽取 `VALUES(x)` 引用，在 message 里直接点出该改成 `EXCLUDED.x`

## R007 · AUTO_INCREMENT

- **级别**：BLOCKER
- **改写**：`id BIGINT AUTO_INCREMENT` → `id BIGINT GENERATED BY DEFAULT AS IDENTITY`（或显式 `SEQUENCE` + `nextval`）
- **数据迁移注意**：序列必须 `setval` 到现有最大 id 之后，否则第一条插入就主键冲突。规则无法判断，只在 message 里提示

## R008 · GROUP_CONCAT

- **级别**：BLOCKER
- **改写**：`GROUP_CONCAT(col ORDER BY x SEPARATOR ',')` → `STRING_AGG(col, ',' ORDER BY x)`
- **注意**：`SEPARATOR` 是关键字，在 PG 里要变成 `STRING_AGG` 的**第二个位置参数**；不写 SEPARATOR 时 PG 必须显式给分隔符

## R009 · 反引号标识符

- **级别**：MAJOR
- **检测**：`` `xxx` `` 形式的标识符
- **改写**：`` `col` `` → `"col"`（或小写时直接去掉引号）
- **误报风险**：中。字符串字面量里的反引号也会命中。取舍是故意的：真问题远比字面量常见，
  且报告会展示 snippet，人工一眼可排除
- **附带问题**：MySQL 在 Windows 下标识符大小写不敏感，PG 会折叠为小写，改名场景需单独核对

## R010 · LIMIT 无 ORDER BY

- **级别**：MINOR
- **检测**：语句含 `LIMIT` 且**完全不含** `ORDER BY`
- **为什么危险**：不是语法错误，是**结果不确定**。两库访问路径不同、物理行序不同，同一页会返回不同记录，且日志里不会有任何痕迹
- **已知简化**：子查询内部有 `ORDER BY` 也算"有排序"，不再细分
- **误报风险**：低

## R011 · MyBatis `<foreach>`

- **级别**：MINOR
- **检测**：语句内出现过 `<foreach>` 标签（解析器会把标签名记录到 `SqlStatement.dynamicTags`）
- **为什么需要人工复核**：
  1. 空集合 → 生成 `IN ()`，**两库都是语法错误**，MySQL 在少数上下文下能容忍
  2. 批量插入通常与 `INSERT IGNORE` / `ON DUPLICATE KEY` 一起出现（见 R005 / R006）
  3. **PostgreSQL 单语句绑定参数上限 65535**，MySQL 侧没这个限制，大批量插入迁移后会直接失败
- **为什么不判为 BLOCKER**：规则不知道集合大小与是否为空，这是"请复核"标记，不是缺陷判定

## R012 · REGEXP / RLIKE

- **级别**：MAJOR
- **改写**：`col REGEXP 'p'` → `col ~ 'p'`；大小写不敏感用 `~*`
- **注意**：正则方言本身也有差异（转义、字符类），只换运算符不等于等价

## R013 · JSON_EXTRACT

- **级别**：MAJOR
- **改写**：`JSON_EXTRACT(c, '$.k')` → `c ->> 'k'`（返回 text）/ `c -> 'k'`（返回 jsonb）
- **最容易踩的坑**：该用 `->>` 的地方用了 `->`，结果带着引号去比较，**不报错但永远不相等**

## R014 · TINYINT(1)

- **级别**：MINOR
- **改写**：`flag TINYINT(1)` → `flag BOOLEAN`
- **关键提醒**：**不要**把 `TINYINT(1)` 映射成 `SMALLINT`。数据能存，但 JDBC `getBoolean()` 与 ORM 的 boolean 映射会失效

## R015 · ON UPDATE CURRENT_TIMESTAMP

- **级别**：MAJOR
- **改写**：去掉列级 `ON UPDATE`，改用 `BEFORE UPDATE` 触发器或在应用层维护 `updated_at`
- **为什么容易漏**：迁移后语句照常成功，只是**这个字段再也不会自动更新**，往往几个月后才被发现

## R016 · `<=>` NULL 安全等于

- **级别**：BLOCKER
- **改写**：`a <=> b` → `a IS NOT DISTINCT FROM b`
- **注意**：这是运算符不是函数，没有等价的符号；写在 `<if>` 长表达式里很容易被漏掉

## R017 · `ORDER BY DESC` + `LIMIT`

- **级别**：MINOR
- **检测**：语句同时含 `LIMIT` 与 `ORDER BY ... DESC`
- **差异**：MySQL 认为 NULL 最小（ASC 在前、DESC 在后）；PG 认为 NULL 最大（ASC 在后、DESC 在前）
- **为什么限定 `LIMIT`**：不加 `LIMIT` 时排序差异只是"顺序不同"，加了 `LIMIT` 就变成"**哪条记录进第一页**不同"
- **改写**：显式写 `NULLS LAST` / `NULLS FIRST`

## R018 · 索引前缀长度

- **级别**：MAJOR
- **检测**：`KEY idx (col(10))`
- **改写**：`CREATE INDEX idx ON t (left(col, 10))`
- **关键提醒**：表达式索引只有在查询用**同一表达式**时才会命中，所以 SQL 也要一起改。
  规则会从匹配中抽出索引名、列名、长度，直接给出可用的 `CREATE INDEX` 语句

## R019 · REPLACE INTO

- **级别**：MAJOR
- **改写**：`REPLACE INTO` → `INSERT ... ON CONFLICT DO UPDATE`
- **语义差异**：MySQL `REPLACE` 是**先删后插** —— 触发器会触发两次，自增主键会变。
  改成 upsert 是行为变更（通常正是想要的），但必须是**由人做出的决定**

## R020 · 日期函数

- **级别**：BLOCKER
- **检测**：`DATE_ADD` / `DATE_SUB` / `STR_TO_DATE` / `UNIX_TIMESTAMP`
- **改写**：
  ```sql
  DATE_ADD(c, INTERVAL 1 DAY)  ->  c + INTERVAL '1 day'
  DATE_SUB(c, INTERVAL 1 DAY)  ->  c - INTERVAL '1 day'
  STR_TO_DATE(s, '%Y-%m-%d')   ->  TO_DATE(s, 'YYYY-MM-DD')
  UNIX_TIMESTAMP()             ->  EXTRACT(EPOCH FROM now())
  ```
- **注意**：格式串语法同时要换（`%Y` → `YYYY`），和 R002 一个道理

## 自动改写（v0.4）

`--fix` 只执行**等价**改写；`--fix-all` 连需要人工确认的一起执行。判断标准只有一条：
**改写后行为是否与原来完全等价**。

| 规则 | `--fix` | `--fix-all` | 覆盖范围 | 不覆盖时怎么办 |
|---|---|---|---|---|
| R001 IFNULL | ✅ | ✅ | 全部 | —— |
| R004 分页语法 | ✅ | ✅ | 全部（含 MyBatis 占位符） | —— |
| R016 `<=>` | ✅ | ✅ | 原始符号 + XML 转义形式 `&lt;=&gt;` | —— |
| R002 `DATE_FORMAT` | ❌ | ✅ | 常见格式符（`%Y %m %d %H %i %s %f %p %T %r`…） | 遇 `%W` / `%M` 等 locale 相关格式符**原样保留**，继续报错 |
| R009 反引号 | ❌ | ✅ | 全部 | 改完需确认**大小写折叠**策略（PG 的 `"User"` 区分大小写） |
| R013 `JSON_EXTRACT` | ❌ | ✅ | 单层路径 `$.key` | 多级路径需拆成链式 `->>`，留给人工 |

**其余 14 条规则不支持自动改写**：改写形状取决于主键结构、业务约束或事务边界。
逐条原因与可选项见 [manual-decisions.md](manual-decisions.md)。

### 三条实现约束

1. **幂等**：`fix(fix(x)) == fix(x)`。迁移工具会被反复执行，不收敛的改写比不改写更危险。
   `RuleFixTest` 对每条规则都断言了这一点。
2. **不猜**：遇到无法安全判定的写法（未知格式符、多级 JSON 路径）就原样返回那一段，
   让规则继续把它报出来 —— 静默改错比报错难查一百倍。
3. **改后重扫**：`--fix` 的唯一验收标准是"重新扫描后问题数下降"。
   数字会直接打印出来，也写进报告。

### XML 的一个额外坑

Mapper XML 里 `<=>` 含 `<`，必须写成 `&lt;=&gt;`，否则文件本身就不是合法 XML。
检测与改写都要认转义形式 —— 这个 bug 是被 `AutoFixerTest` 的 fixture 逼出来的：
早期版本对真实 Mapper 上的 `<=>` 是瞎的。
